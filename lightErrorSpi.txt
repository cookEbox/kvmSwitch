SPI LED troubleshooting report
==============================

Date of report: 2026-10-14
Project: kvmSwitch

Purpose
-------

The test program was changed to drive 36 LEDs through /dev/spidev0.0 and
display several frames for five seconds each. The intended test was:

  1. All 36 LEDs on.
  2. LED 4 off, all other LEDs on.
  3. Multiple LEDs off / alternating LEDs off.
  4. All LEDs off.

The program prints a label before each frame and keeps the SPI device open
while displaying the final state.

Chronology of changes and observed results
-------------------------------------------

1. Initial LED test change

Changed app/Main.hs to stop waiting for key presses, turn on the first four
LEDs in white, and hold them for five seconds. The old key-press loop was
commented out. The LED renderer was also cleaned up so it rendered the list
passed to it instead of retaining unused single-LED test variables.

Observed result:

  - Two LEDs were white.
  - The third LED was yellow.
  - The fourth LED was off.

2. Initial four-frame test

Added frames for all-on, LED 4 off, several LEDs off, and all-off. Each
intermediate state was intended to be held for five seconds.

3. SK6812 32-bit experiment

Changed src/OneWire/LedSpi.hs to encode four bytes per pixel, assuming an
SK6812 RGBW device with GRBW ordering.

Observed result:

  - LEDs appeared as different colours: magenta, turquoise, yellow, and
    white for LEDs 1 through 4.

This indicated that the strip was behaving like a 24-bit RGB stream for the
test data, so the 32-bit change was reverted.

4. Restored 24-bit GRB encoding and changed SPI speed

Restored 24-bit GRB encoding and changed the SPI clock from 3.2 MHz to
2.4 MHz. The 2.4 MHz rate was used in an earlier version of the project.

5. Kept one SPI connection open

Changed app/Main.hs so one SPI connection was opened for the entire sequence,
rather than opening and closing SPI for every frame. Added showFrame to print
the frame name and hold each frame for five seconds.

6. Replaced hand-written test lists

Replaced the long hand-written lists with generated lists:

  testLed1 = replicate 3 whiteLed <> [offLed] <> replicate 32 whiteLed
  testLed2 = concat (replicate 18 [whiteLed, offLed])

This guarantees that both test frames contain exactly 36 pixels.

7. Repeated-frame experiments

Several experiments sent frames twice, repeated the final all-off frame, and
added a final frame labelled "all off (Hellooooo)". These were attempts to
deal with a suspected missed SPI transfer or latch.

8. Partial-write experiment

Changed the SPI renderer to loop until fdWrite had written the entire
payload. This was reverted because splitting a pixel frame over multiple
SPI write transactions can itself disturb the LED latch timing.

The current renderer performs one fdWrite per frame and checks that the
returned byte count equals the complete payload length.

9. Scanner isolation

The GPIO keyboard scanner was removed from the LED test path. The current
LED test does not load the keyboard configuration or call startScanner. It
only opens SPI and sends the LED frames.

10. Current final-state handling

The current test sends the all-off frame three times:

  showFrame spi "all off" allOff
  showFrame spi "all off (final latch)" allOff
  showFrame spi "all off (Hellooooo)" allOff

It then keeps SPI open for 60 seconds. The current source therefore has no
command after these all-off frames that intentionally turns the LEDs on.

Light sequences reported during testing
----------------------------------------

The following sequences were reported, in order:

  A. Two white LEDs, third yellow, fourth off.

  B. All on, then finally all off.

  C. All on, all on, alternating LEDs off, all on.

  D. All on, all on, alternating LEDs off, all on, all off.

  E. All on, all on, alternating LEDs off, all on, all off, all on.

  F. After isolating the LED test from the GPIO scanner and rebooting the Pi:
     all on, all on, alternating LEDs off, all on, all off, all on.

Current code versus reported behaviour
--------------------------------------

Current intended frame sequence:

  Code frame 1: all 36 LEDs on.
  Code frame 2: LED 4 off; the other 35 LEDs on.
  Code frame 3: LEDs 1, 3, 5, ..., 35 on; LEDs 2, 4, 6, ..., 36 off.
  Code frame 4: all 36 LEDs off.
  Code frame 5: all 36 LEDs off.
  Code frame 6: all 36 LEDs off.
  Then: no new LED frame; SPI remains open for 60 seconds.

Reported visual sequence F:

  Light state 1: all on.
  Light state 2: all on.
  Light state 3: alternating LEDs off.
  Light state 4: all on.
  Light state 5: all off.
  Light state 6: all on.

The reported sequence does not match the current Haskell frame values. In
particular, the current code contains no all-on frame after the three final
all-off frames. The discrepancy is therefore in how the SPI payload is being
interpreted, latched, or observed by the LED hardware, rather than in the
list construction in Main.hs.

Build verification
------------------

After the source changes, cabal build compiled and linked the executable.
The command also reported an unrelated inability to write Cabal's log file
because the environment's Cabal cache/log location was read-only.

Current SPI assumptions to compare with the working Python implementation
-------------------------------------------------------------------------

  - Device: /dev/spidev0.0
  - SPI mode: 0
  - Bits per word: 8
  - Clock: 2,400,000 Hz
  - Pixel format: 24-bit GRB
  - Encoding: each LED data bit becomes SPI symbols 100 or 110
  - Frame size: 36 pixels * 24 bits * 3 = 324 SPI bytes
  - One fdWrite call per frame
  - 200 microsecond latch delay after each frame

The next useful comparison is the working Python implementation's SPI mode,
clock, pixel byte order, symbol encoding, transfer method, and reset/latch
handling.
